# ビジネスロジックの不備（Business Logic Flaws）

> **スコープ**: アプリの「正規の機能」を仕様外の順序・値・回数・タイミングで使うことで成立する欠陥の検出。価格/数量の改ざん、ワークフロー順序の迂回、機能回数制限の突破、レースコンディション、整合性チェック欠落、想定外入力までを扱う。**入力をサニタイズする話（XSS/SQLi 等）ではなく「入力は正規だが組み合わせ・順序・前提が悪用される」話**。認可そのものの穴は `IDOR.md`、パラメータ改ざんによる権限昇格は `Command_Injection.md` の該当節を参照。

## 着火条件

- 多段ステップのフロー（カート → 住所 → 支払い → 確定／登録 → メール確認 → 有効化）がある
- 金額・数量・ポイント・残高・割引など**数値の状態をサーバーが保持**している
- 「1人1回」「1日N回」のような**回数・頻度の制限**がある機能（クーポン・投票・OTP・無料トライアル・出金）
- 価格・割引・税・送料・合計が**複数のリクエストにまたがって計算**される
- フォームに hidden field・readonly・disabled な値（価格・ユーザーID・ロール・ステータス）がある
- 「ユーザーは普通こう操作するはず」という暗黙の前提に依存した実装が見える

## 環境前提

- 実行環境: テスター端末
- 必要なツール: Burp Suite（Repeater で状態遷移を手動操作・Intruder で回数試行・Turbo Intruder / Repeater の「Send group in parallel (single-packet attack)」でレースコンディション）/ `curl` + シェルループ（オフライン代替・並列は `&` ＋ `wait`）
- オフライン代替: 並列リクエストは `curl` を `&` でバックグラウンド多重起動 → `wait` で同期。単一パケット攻撃ほど精度は出ないが TOCTOU の多くは捕捉できる

## 先に確認すること

- **正常系を必ず先に1周し、全リクエストを Burp history に溜める**。ビジネスロジックは「正規フローのどのリクエストで何の値が確定するか」を把握しないと改ざんポイントが見えない。各ステップの**サーバー応答に状態（合計金額・在庫・ステップ番号・ステータス）が反映される箇所**を記録する
- **アカウントは2つ用意する**（攻撃者用と被害者/比較用）。「自分の操作が他者・全体にどう影響するか」を見るのがロジック系の基本
- **数値はサーバー側で再計算されているか／クライアント値を信じているか**を最初に切り分ける。改ざんした値が応答に echo されるだけと、実際に課金/残高に反映されるのは別物

**ビジネスロジック不備の探し方（観点の軸）:**

| 軸 | 問い | 代表パターン |
|---|---|---|
| データ検証（BUSL-01）| サーバーは値の範囲・整合を再検証しているか | 負数・極大・小数・通貨・hidden field 改ざん |
| リクエスト偽造（BUSL-02）| UI で出せない値・組み合わせを直接送れるか | UI 非表示パラメータ・別ユーザー文脈の値注入 |
| 整合性（BUSL-03）| 不変であるべき値を後から変えられるか | Mass Assignment・確定後の値書き換え |
| プロセスタイミング（BUSL-04）| 同時/規定外タイミングで二重取りできるか | レースコンディション・TOCTOU |
| 回数制限（BUSL-05）| 「1回だけ」が本当に1回か | クーポン再利用・OTP 総当り・トライアル無限化 |
| ワークフロー順序（BUSL-06）| ステップを飛ばして確定できるか | 支払いスキップ・確認スキップ・強制ブラウジング |
| 不正利用防御（BUSL-07）| 異常な使い方を検知/抑止するか | 自動化検知なし・異常量の操作を素通り |

**攻撃者の思考トレース:** ビジネスロジック不備は「壊れた入力」を送る攻撃ではなく「**正しい入力を、設計者が想定しなかった値・順序・回数・タイミングで送る**」攻撃。だからスキャナでは出ない。鍵は「このフローはユーザーが○○すると暗黙に仮定している。その仮定を破ったら？」を各ステップで問うこと。下の §1（最も基本＝値の改ざん）から §8（最も応用＝前提の悪用）へ、観測しやすい順に並べてある。

## 1. データ検証不備 — 数値・通貨・hidden field の改ざん（WSTG-BUSL-01）

最も基本。クライアントから来る値をサーバーが再検証せず信じる欠陥。

**コマンド:**

```bash
# [Attacker] hidden field の価格をそのまま信じるか（フォームの price を改ざんして送信）
curl -s -X POST http://[TARGET]/cart/add \
  -H "Cookie: session=[MY_SESSION]" \
  -d "product_id=10&price=1&quantity=1"

# [Attacker] 負数で「マイナス購入＝残高・ポイントが増える」を狙う
curl -s -X POST http://[TARGET]/cart/update \
  -H "Cookie: session=[MY_SESSION]" \
  -d "product_id=10&quantity=-5"

# [Attacker] 極大値で整数オーバーフロー / 在庫無視を狙う
curl -s -X POST http://[TARGET]/cart/update \
  -H "Cookie: session=[MY_SESSION]" -d "product_id=10&quantity=99999999999"

# [Attacker] 小数・通貨ずらし（端数丸め・通貨混同を狙う）
curl -s -X POST http://[TARGET]/cart/update \
  -H "Cookie: session=[MY_SESSION]" -d "product_id=10&quantity=0.1&currency=IDR"
```

**観測される出力 → 次のアクション:**

| 出力 | 示唆 | 次のアクション |
|---|---|---|
| 改ざんした `price` が合計に反映される | サーバー側で価格を再取得していない | 確定まで進めて課金額が改ざん値か確認（§6 で支払いまで） |
| `quantity=-5` で合計がマイナス／残高加算 | 符号の検証なし | 返金・残高増加に繋がるか確定フローで検証 |
| 極大数量で合計が小さい値/負値になる | 整数オーバーフロー | オーバーフロー境界（2^31, 2^63 付近）を二分探索で特定 |
| `currency` を低額通貨にすると同じ数字で安くなる | 通貨と金額の整合未検証 | 決済通貨と請求通貨の不一致を悪用 |
| 改ざん値が応答に出るが合計は変わらない | サーバー側で再計算済み | echo されるだけ。§2 リクエスト偽造 / §3 整合性へ |

**注意:** 「応答に改ざん値が映る」≠「成立」。**最終的に課金額・残高・在庫に反映されて初めて finding**。確定（§6）まで通して金銭影響を確認する。テスト購入が実際に決済されうる本番では、決済直前の確認画面の金額表示で判定し、確定ボタンは合意の上でのみ押す。

## 2. リクエスト偽造 — UI で出せない値・組み合わせを直接送る（WSTG-BUSL-02）

UI のドロップダウン・ボタンで選べない値や、UI には無いパラメータをサーバーが受理するか。

**コマンド:**

```bash
# [Attacker] UI で選べない選択肢（在庫切れ商品・非公開プラン・終了したキャンペーン）を直接指定
curl -s -X POST http://[TARGET]/subscribe \
  -H "Cookie: session=[MY_SESSION]" -d "plan=enterprise&billing=free"

# [Attacker] UI に存在しないパラメータを推測して付与（割引率・税率・ロール）
curl -s -X POST http://[TARGET]/checkout \
  -H "Cookie: session=[MY_SESSION]" \
  -d "items=10&discount_percent=100&tax_exempt=true"

# [Attacker] クライアント側 JS でのみ検証している入力をバイパス（直接 API を叩く）
curl -s -X POST http://[TARGET]/api/transfer \
  -H "Cookie: session=[MY_SESSION]" -H "Content-Type: application/json" \
  -d '{"to":"[ATTACKER_ACCT]","amount":1000000}'
```

**観測される出力 → 次のアクション:**

| 出力 | 示唆 | 次のアクション |
|---|---|---|
| UI 非表示の選択肢が受理される | サーバーが「UI で出せる値しか来ない」と仮定 | その値で得られる優位（無料プラン・割引）を確定まで通す |
| 推測した追加パラメータ（`discount_percent` 等）が効く | 隠しパラメータの未防御 | パラメータ名を辞書化して総当り（`role`,`is_admin`,`credit`,`balance`…）→ §3 Mass Assignment |
| JS 検証していた制約（上限金額・桁数）が API では効かない | 検証がクライアント側のみ | API 直叩きで制約超過の値を送る |
| 全て 400 / サーバーが値を拒否 | サーバー側でホワイトリスト検証 | §6 ワークフロー順序 / §8 前提の悪用へ |

**注意:** 隠しパラメータの推測は、正常系レスポンスの JSON フィールド名・JS バンドル・API ドキュメント・別の類似エンドポイントから語彙を集めると当たりやすい。`IDOR.md` の「他エンドポイントから語彙/ID を集める」発想と同じ。Mass Assignment（受理されたフィールドで権限・残高を書き換える）は §3 へ。

## 3. 整合性チェック不備 — Mass Assignment・確定後の書き換え（WSTG-BUSL-03）

不変であるべき値（確定済み価格・ステータス・所有者・ロール）を後から変えられる欠陥。

**コマンド:**

```bash
# [Attacker] Mass Assignment — モデルの保護されるべき属性を更新リクエストに混ぜる
curl -s -X PATCH http://[TARGET]/api/account \
  -H "Cookie: session=[MY_SESSION]" -H "Content-Type: application/json" \
  -d '{"name":"test","role":"admin","email_verified":true,"balance":99999}'

# [Attacker] 注文確定後にステータス/金額を書き換える（状態機械の不備）
curl -s -X PATCH http://[TARGET]/api/orders/[MY_ORDER_ID] \
  -H "Cookie: session=[MY_SESSION]" -H "Content-Type: application/json" \
  -d '{"status":"paid","total":0}'

# [Attacker] クーポン適用後に金額を再送して二重割引・割引固定を狙う
curl -s -X POST http://[TARGET]/cart/apply_coupon \
  -H "Cookie: session=[MY_SESSION]" -d "code=SAVE10"
curl -s -X POST http://[TARGET]/cart/apply_coupon \
  -H "Cookie: session=[MY_SESSION]" -d "code=SAVE10"   # 同じコードを再適用
```

**観測される出力 → 次のアクション:**

| 出力 | 示唆 | 次のアクション |
|---|---|---|
| `role`/`email_verified`/`balance` が反映される | Mass Assignment（strong params 未設定） | 権限昇格・残高改ざんへ。権限系は `Command_Injection.md`（is_admin）も参照 |
| 確定後に `status=paid` / `total=0` が通る | 状態遷移の検証なし（未払いを支払い済みに） | 未決済で商品/サービスを取得できるか確認 |
| 同一クーポンの2回目が「割引額」をさらに引く | 冪等性・適用済みフラグ無し | 適用回数を増やして合計を 0 以下に |
| 保護属性が無視される/エラー | allowlist で属性制御済み | §4 レース / §6 順序へ |

**注意:** Mass Assignment は ORM の「全フィールド一括代入」既定挙動（Rails の `permit` 漏れ・Spring の `@ModelAttribute` バインド・Node の `Object.assign(model, req.body)` 等）が原因。**正常系レスポンスに出るフィールド名をそのまま更新ボディに足す**のが一番当たる。確定後の書き換えで実データを変えた場合は**原状回復必須**（元の status/total に戻す）。

## 4. プロセスタイミング — レースコンディション / TOCTOU（WSTG-BUSL-04）

「残高を確認してから引く」「使用済みか確認してから使う」の**確認と実行の間（TOCTOU）**に同時リクエストを差し込み、1回分の権利を多重行使する。

**コマンド:**

```bash
# [Attacker] 同一処理を並列多重送信（クーポン/出金/在庫予約の二重取り）
# オフライン: curl をバックグラウンド多重 → wait で同期着弾
for i in $(seq 1 30); do
  curl -s -X POST http://[TARGET]/wallet/withdraw \
    -H "Cookie: session=[MY_SESSION]" -d "amount=100" &
done
wait
# 残高が 100×1 だけ減って複数回の出金が成功していれば TOCTOU 成立
```

```text
# [Attacker] Burp 推奨手順（精度が段違い）
# 1. 対象リクエストを Repeater のタブグループにまとめる（同一リクエストを N 個複製）
# 2. グループのドロップダウン → "Send group in parallel (single-packet attack)"
#    HTTP/2 の single-packet attack でネットワークジッタを排除し、サーバー処理を真に同時化する
# 3. HTTP/1 のみの対象は "last-byte sync"。Turbo Intruder の race-single-packet.py も可
```

**観測される出力 → 次のアクション:**

| 出力 | 示唆 | 次のアクション |
|---|---|---|
| N 回送って残高が1回分しか減らない | TOCTOU（確認と更新が非アトミック） | 並列数を変えて再現性確認 → 利得（多重出金・在庫超過予約）を確定 |
| 「1回限り」クーポンが並列で複数成立 | 使用済みフラグ更新前に多重通過 | 割引/ポイントの多重適用 |
| 招待・トライアル・投票が並列で上限突破 | カウンタのインクリメントが非アトミック | 上限を超えた付与を確認 |
| 並列でも常に1回だけ成功 | ロック/一意制約/アトミック更新あり | §5 回数制限の別経路 / §6 順序へ |

**注意:** 成功率はサーバーの処理時間とネットワーク同時性に依存する。`curl &` の素朴な並列で出なくても、**single-packet attack（HTTP/2）なら出る**ことが多い。逆に DB の一意制約（`UNIQUE(coupon_id, user_id)`）やトランザクション行ロックがあると塞がれる。多重成立で実残高/在庫を動かしたら**原状回復**（過剰付与の取り消し）。
> 原理（確認と実行の間に状態が変わる TOCTOU の一般論）→ サーバー側のアトミック更新・楽観ロックの有無で成否が決まる。

## 5. 機能回数制限の不備 — 「1回だけ」が本当に1回か（WSTG-BUSL-05）

クーポン・OTP・パスワードリセット・無料トライアル・投票・出金など、回数/頻度に意味がある機能の上限を論理で突破する。

**コマンド:**

```bash
# [Attacker] OTP / PIN の総当り（試行回数制限・ロックアウトの有無を見る）
for code in $(seq -w 0000 9999); do
  resp=$(curl -s -o /dev/null -w "%{http_code}" -X POST http://[TARGET]/verify_otp \
    -H "Cookie: session=[MY_SESSION]" -d "otp=$code")
  echo "$code -> $resp"
done
# 4xx でロックされず延々と試せれば総当り可能

# [Attacker] トライアル/特典の再取得（識別子を変えて無限化）
curl -s -X POST http://[TARGET]/start_trial \
  -H "Content-Type: application/json" \
  -d '{"email":"user+tag1@example.com"}'   # +tag / ドット / 別ドメインで同一人物を別人扱い

# [Attacker] クーポンを別アカウント・別セッションで使い回す
curl -s -X POST http://[TARGET]/cart/apply_coupon \
  -H "Cookie: session=[SECOND_ACCT_SESSION]" -d "code=WELCOME"
```

**観測される出力 → 次のアクション:**

| 出力 | 示唆 | 次のアクション |
|---|---|---|
| OTP を 4xx ロックなしで延々試せる | 試行回数制限なし（→ 認証バイパス） | 総当りで突破。ロックアウト有無は `Account_Lockout_Recon.md` も参照 |
| `email+tag@` / ドット差分で別人扱い | 正規化せず一意判定 | 同一人物で無限トライアル/特典 |
| 「1人1回」クーポンが別アカウントで再利用 | グローバル一意でなくユーザー単位ですらない | 大量アカウント or レース（§4）で増幅 |
| パスワードリセットトークンが期限切れにならない/再利用可 | トークン無効化漏れ | 古いトークンで乗っ取り |
| 上限到達で確実に拒否される | サーバー側でカウンタ管理 | §4 レースで上限突破を試す / §6 順序へ |

**注意:** メールの正規化漏れ（`a.b@` と `ab@`、`+tag`、大文字小文字、使い捨てドメイン）は「同一人物を別人と誤認」させる定番。回数制限が**ユーザー単位かグローバルか**を見極める。OTP 総当りは本番ではアカウントロック・アラートを誘発しうるので合意必須。

## 6. ワークフロー順序の迂回 — ステップ飛ばし・支払いスキップ（WSTG-BUSL-06）

多段フローの中間ステップ（支払い・本人確認・承認）を飛ばして最終状態に到達する。「前のステップを必ず通っている」という暗黙の前提を破る。

**コマンド:**

```bash
# [Attacker] 正常系の最終確定リクエストだけを、支払いステップを飛ばして直接送る
# （正常フローを1周して各ステップの URL/パラメータを Burp history から把握しておく）
curl -s -X POST http://[TARGET]/checkout/complete \
  -H "Cookie: session=[MY_SESSION]" -d "order_id=[MY_ORDER_ID]"

# [Attacker] 支払い成功コールバックを自分で叩く（決済 PSP からの戻りを偽装）
curl -s -X POST http://[TARGET]/payment/callback \
  -H "Content-Type: application/json" \
  -d '{"order_id":"[MY_ORDER_ID]","status":"success","signature":""}'

# [Attacker] 多段登録（メール確認 → 有効化）の確認ステップを飛ばして保護機能へ
curl -s http://[TARGET]/dashboard -H "Cookie: session=[UNVERIFIED_SESSION]"
```

**観測される出力 → 次のアクション:**

| 出力 | 示唆 | 次のアクション |
|---|---|---|
| 支払い前に `complete` が注文を確定する | ステップ間の状態検証なし | 未払いで商品/サービス取得を確認（金銭影響 finding） |
| 自作 callback で `status=success` が通る | コールバック署名/真正性の未検証 | 任意注文を「支払い済み」化。署名必須なら §3 整合性へ |
| メール未確認でも保護機能にアクセスできる | 確認ステップが UI 上の誘導のみ | 未確認状態で到達できる機能を列挙 |
| 中間ステップ必須で弾かれる（順序トークン検証） | サーバー側でステート管理 | §8 前提の悪用 / 別エンドポイントの順序欠落を探す |

**注意:** これは「強制ブラウジング（forced browsing）」のロジック版。鍵は**正常系を1周して各ステップの真の遷移を把握**してから、途中を抜く・順序を入れ替える・同じステップを2回踏むこと。決済 callback 偽装は PSP の署名検証があると塞がれる（→ 署名の検証不備は `JWT_Attacks.md` / 署名なしは §3）。実際に注文を確定させると在庫・会計に影響するため、本番ではドライランの可否を合意する。

## 7. 不正利用への防御欠如 — 異常な使い方が素通りするか（WSTG-BUSL-07）

正規機能を「人間がやらない量・速度・組み合わせ」で使ったときに、検知・抑止・レート制限が働くか。単体の脆弱性というより**他のロジック攻撃を増幅できるかの確認**。

**コマンド:**

```bash
# [Attacker] 同一機能を高速大量に呼ぶ（レート制限/異常検知の有無）
for i in $(seq 1 200); do
  curl -s -o /dev/null -w "%{http_code}\n" http://[TARGET]/api/search?q=$i \
    -H "Cookie: session=[MY_SESSION]"
done | sort | uniq -c
# 全て 200 で 429（Too Many Requests）が出なければレート制限なし

# [Attacker] 在庫を全量カートに確保して売り切れさせる（在庫枯渇 DoS の業務影響）
curl -s -X POST http://[TARGET]/cart/add \
  -H "Cookie: session=[MY_SESSION]" -d "product_id=10&quantity=[STOCK_TOTAL]"
```

**観測される出力 → 次のアクション:**

| 出力 | 示唆 | 次のアクション |
|---|---|---|
| 大量呼び出しで 429 が一切出ない | レート制限/異常検知なし | §4 レース・§5 総当り・列挙系を増幅できる前提として記録 |
| 在庫を全確保したまま放置で他者が買えない | カート予約の TTL/上限なし（在庫枯渇） | 業務影響（販売妨害）として報告。実在庫を動かすので合意必須 |
| 一定回数で CAPTCHA / ロック / アラート | 不正利用検知あり | 検知閾値を測り、その下で §4/§5 を実施 |

**注意:** 在庫枯渇・大量送信は**業務影響（可用性）に直結する高リスク行為**。本番では原則禁止または明示合意が必要（[HIGH IMPACT] 相当）。検証は「検知が存在するか」の確認に留め、実際に在庫を枯渇させる・サービスを停止させる操作は合意なしに行わない。

## 8. 前提の悪用 — 想定外入力・ユーザー行動の仮定崩し（PortSwigger 系）

「ユーザーは普通こうする」という開発者の暗黙仮定を破る。明確な WSTG ID は無いが、ロジック不備の中核的な観点。

**着眼点（コマンドより「問い」が主体）:**

| 開発者の暗黙の仮定 | 破り方 | 成立例 |
|---|---|---|
| 「数量は正の整数」 | 負数・0・小数・極大（§1）| マイナス購入で返金/残高増 |
| 「金額は変わらない」 | 確定後に再送/別レートで再計算（§3）| 確定後の値下げ |
| 「このパラメータは UI 由来」 | UI 非表示の値を直接送る（§2）| 終了キャンペーン・非公開プランの取得 |
| 「前のステップを必ず通る」 | 中間ステップ飛ばし（§6）| 未払い確定 |
| 「1人=1メール=1回」 | メール正規化漏れ・別アカウント（§5）| 特典無限化 |
| 「同時には1回しか来ない」 | 並列送信（§4）| 二重取り |
| 「ユーザーは自分のデータしか触らない」 | 他者IDを送る（IDOR）| 越権参照・操作 |
| 「入力は妥当な範囲」 | 文字列に数値、数値に文字列、巨大入力、Unicode/絵文字、null/空 | 型変換・丸め・切り詰めの隙 |

**コマンド（型・境界の崩し）:**

```bash
# [Attacker] 数値を期待する箇所に文字列/配列、文字列箇所に数値・null を送る
curl -s -X POST http://[TARGET]/api/order \
  -H "Cookie: session=[MY_SESSION]" -H "Content-Type: application/json" \
  -d '{"quantity":"1e3","price":null,"coupon":["A","B"]}'

# [Attacker] 巨大入力/特殊文字で切り詰め・正規化のずれを誘発
curl -s -X POST http://[TARGET]/register \
  -d "username=admin                         &..."   # 末尾空白で既存ユーザーと衝突/別扱い
```

**観測される出力 → 次のアクション:**

| 出力 | 示唆 | 次のアクション |
|---|---|---|
| `"1e3"` が 1000 と解釈される | 文字列→数値の暗黙変換 | 指数表記/16進で範囲チェック回避 |
| 末尾空白付き `admin ` が別ユーザーとして作れる | 入力正規化と一意判定の不一致 | 既存特権ユーザーへのなりすまし下地 |
| 配列/null でエラー画面に内部情報 | 型検証なし | スタックトレース → 別の脆弱性の手掛かり |
| 全て厳格に型・範囲検証される | 防御あり | ロジック面は堅い。入力系（SQLi/XSS）へ軸を移す |

**注意:** このカテゴリは「アプリ固有の業務ルール」を理解しているほど刺さる。正常系を触りながら「この機能、もし○○したら破綻するのでは？」というメモを溜めるのが上達の近道。型崩しはエラー経由で情報漏洩（スタックトレース）を生むこともあり、別系統の脆弱性への入口になる。

## 刺さらなかったとき（全体）

| 観測される症状 | 推定原因 | 次の手 |
|---|---|---|
| 改ざん値が応答に出るが課金/残高に無影響 | サーバー側で再計算・再取得している | echo 確認だけでは finding にならない。§6 で確定まで通して金銭影響を見る |
| 並列送信しても常に1回だけ成功 | アトミック更新/一意制約/行ロック | single-packet attack（HTTP/2）で再試行 → それでも不可なら回数制限は堅い |
| 隠しパラメータ総当りが全て無視 | allowlist バインド（strong params） | レスポンス JSON のフィールド名に限定して再試行 |
| ステップ飛ばしが順序トークンで弾かれる | サーバー側ステート管理あり | 別フロー（パスワード変更・退会・返金）に順序欠落がないか横展開 |
| どの値もサーバーが厳格検証 | ロジック面は堅牢 | 入力サニタイズ系（SQLi/XSS/SSRF）へ軸を移す |

## 注意点・落とし穴

- **「応答に改ざん値が映る」≠「成立」**: 最終的に金銭・残高・在庫・権限に反映されて初めて finding（§1・§3 の注意参照）
- **正常系を1周してから壊す**: 各ステップで何の状態がいつ確定するかを把握しないと改ざんポイントが見えない（§6 注意参照）
- **アカウント2つで「他者/全体への影響」を見る**: ロジック不備の多くは単独セッションでは見えない
- **実データを動かしたら原状回復**: 確定後の status/total 書き換え（§3）・多重付与（§4）・在庫確保（§7）は元に戻す

> **個別ブロック固有の注意は各 §N の「注意:」を参照。**

## 本番での前提

- **事前合意の要否**: ★★★（決済確定・在庫枯渇・OTP 総当り・残高改ざんは書面承認必須）/ ★★（hidden field 改ざん等の読み取り検証は口頭確認可）
- **業務影響リスク**: 高（注文確定・在庫枯渇・サービス停止・実残高変動を伴いうる）。検証は確認画面の金額表示・検知の有無の確認に留め、確定ボタンの押下は合意の上でのみ
- **原状回復必須項目**: ✅ 確定/書き換えた注文・ステータス・金額を元に戻す ✅ 多重付与したポイント/残高/クーポン適用を取り消す ✅ 確保した在庫を解放する ✅ テスト作成アカウントの削除
- **取得情報の取扱**: 他ユーザーの注文/PII に到達した場合は暗号化保管・テスト完了後破棄
- **演習環境での扱い**: 制約なし（HTB / OSCP 等は本セクション全項目をスキップしてよい）
